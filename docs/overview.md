# «Норма рядом» — кратко о проекте и стеке

Короткая версия полного описания проекта (`project-description`) простыми словами: что сделано, из чего состоит, на чём написано и почему, как устроены данные и как всё проверено. Удобно для введения курсовой и подготовки к защите.

## 1. Что это и зачем

Человек, который следит за питанием, дома считает калории по этикеткам, а в кафе выбирает «на глаз» и легко ошибается на 150–200 ккал за обед. Дневники питания отвечают на вопрос «сколько я съел», но не на вопрос «что взять здесь и сейчас».

«Норма рядом» решает именно это:

1. по росту, весу, возрасту, активности и цели считает дневную норму калорий, белков, жиров и углеводов (КБЖУ);
2. делит её на приёмы пищи (завтрак 25%, обед 35%, ужин 30%, перекус 10%);
3. находит заведения рядом и подбирает в них наборы из 1–3 блюд, которые попадают в цель приёма пищи и не содержат исключённых продуктов;
4. честно показывает, насколько можно доверять цифрам: официальная таблица сети, фото меню, проверенное модератором, или оценка;
5. записывает выбранный набор в дневник, учитывает еду из Apple Здоровья и Health Connect.

## 2. Сценарий пользователя

1. Онбординг: параметры тела, исключения (без свинины, без молока и т. п.), согласие на геолокацию или выбор района вручную.
2. Главный экран «Что взять»: остаток нормы на сегодня, выбор приёма пищи, кнопка «Подобрать рядом».
3. Результат: наборы с КБЖУ, ценой, расстоянием и значком достоверности; любое блюдо можно заменить.
4. «Записать в дневник» — остаток нормы пересчитывается.
5. Карта: заведения цветом «есть набор под цель / компромисс / нет», второй режим — цвет по достоверности данных; экран заведения с меню, жалобой «цифры не совпадают» и загрузкой фото меню.
6. Профиль: параметры, норма (можно поправить в процентах), район, связь со «Здоровьем», удаление всех данных.

## 3. Из чего состоит система

| Часть | Что делает | Где в репозитории |
|---|---|---|
| Мобильное приложение | Все экраны, расчёт нормы, дневник, карта; личные данные хранит только на телефоне | `app/` |
| Сервер | Каталог заведений и меню, геопоиск, подбор наборов, приём фото и жалоб | `server/` |
| Админ-панель | Загрузка меню из CSV, модерация фото, разбор жалоб | `server/…/admin` (страницы Thymeleaf) |
| База данных | Сети, точки, блюда, фото, жалобы | PostgreSQL + PostGIS |
| Хранилище фото | Фото меню от пользователей | SeaweedFS (S3-совместимое) |
| Контракты | Общие для клиента и сервера эталоны: API, расчёт нормы, результаты подбора | `contract/` |
| Подготовка данных | Выгрузка заведений из OpenStreetMap, разбор меню сетей, карта | `tool/` |
| Сквозные тесты | Прокликивание приложения и админки в браузере | `e2e/` |

Как они связаны: телефон отправляет на сервер только цель приёма пищи, координаты и исключения — без имени, телефона и идентификатора. Сервер ищет точки в базе, считает наборы и возвращает их. Есть демо-сборка без сервера: каталог и алгоритм встроены в само приложение.

## 5. Архитектура

**Сервер** разбит на модули с проверяемыми границами:

- `catalog` — сети, точки, меню, импорт CSV;
- `geo` — поиск точек рядом;
- `optimizer` — алгоритм подбора, чистый Kotlin без Spring и базы (поэтому его легко тестировать и перенести на телефон);
- `recommendation` — сценарии подбора и HTTP API;
- `intake` — фото меню, распознавание, жалобы;
- `admin` — админ-панель;
- `web` — единый формат ошибок (Problem Details, RFC 9457).

**Клиент** устроен слоями:

- `domain` — модели и расчёт нормы, без Flutter;
- `data` — HTTP-клиент, локальная база, «Здоровье», демо-движок;
- `ui/<экран>` — экран (View) и его состояние (ViewModel на Riverpod).

Данные текут в одну сторону: экран вызывает действие ViewModel, та обращается к репозиторию и публикует новое состояние.

## 6. База данных

| Таблица | Что хранит | Связи |
|---|---|---|
| `chain` | Сеть: название, источник меню, версия меню | — |
| `venue` | Точка: координаты, адрес, дата подтверждения, закрыта ли | → `chain` (у отдельных мест пусто) |
| `menu_item` | Блюдо: КБЖУ, вес, цена, категория, теги исключений, источник и дата | → `chain` (меню сети) или → `venue` (меню точки) |
| `menu_submission` | Фото меню, распознанный текст, статус модерации | → `venue` |
| `item_report` | Жалоба «цифры не совпадают» | → `menu_item` |
| `venue_report` | Сообщение «закрыто или переехало» | → `venue` |

Важные решения:

- геоиндекс GiST по координатам — поиск точек в радиусе за доли миллисекунды;
- индекс GIN по тегам блюд — быстрое исключение продуктов;
- **идемпотентность**: импорт работает как «вставить или обновить» (`INSERT … ON CONFLICT DO UPDATE`), поэтому повторная загрузка того же файла не создаёт дублей; повторная жалоба того же человека не учитывается (`ON CONFLICT DO NOTHING`); любое изменение меню повышает его версию, и кэш перестаёт отдавать устаревшие наборы;
- личные данные (профиль, дневник) на сервер не попадают: они в SQLite на телефоне.

## 7. API

| Запрос | Что делает |
|---|---|
| `GET /api/v1/venues` | Точки на карте в видимой области |
| `GET /api/v1/venues/{id}/menu` | Меню заведения с пометками «подходит / не подходит» |
| `POST /api/v1/combos/search` | Подбор наборов рядом или в одном заведении |
| `POST /api/v1/combos/replace` | Чем заменить блюдо в наборе |
| `POST /api/v1/items/{id}/reports` | Жалоба на цифры блюда |
| `POST /api/v1/venues/{id}/reports` | Сообщение, что заведение закрыто или переехало |
| `POST /api/v1/venues/{id}/menu-photos` | Загрузка фото меню |

Ошибки возвращаются в едином формате Problem Details, частота запросов ограничена (ответ 429 с заголовком `Retry-After`), описание API доступно в Swagger.

## 8. Как считается норма

1. Базовый обмен по формуле Миффлина — Сан Жеора: для женщин 10 × вес + 6,25 × рост − 5 × возраст − 161, для мужчин +5 вместо −161.
2. Умножение на коэффициент активности (от 1,2 до 1,9).
3. Поправка на цель: снижение веса ×0,85, поддержание ×1,0, набор ×1,10.
4. Доли калорий: белки 30%, жиры 30%, углеводы 40% (1 г белка или углеводов — 4 ккал, жиров — 9 ккал).
5. Норма не опускается ниже безопасного минимума: 1200 ккал для женщин, 1500 — для мужчин.

Пример: женщина 25 лет, 165 см, 62 кг, умеренная активность, снижение веса → 1800 ккал: белки 135 г, жиры 60 г, углеводы 180 г.

## 9. Алгоритм подбора простыми словами

Задача похожа на «задачу о рюкзаке»: из меню нужно выбрать 1–3 блюда, чтобы калории попали в окно цели (±10%), белка было не меньше минимума, а жиров и углеводов — не больше максимума.

1. Из меню убираются блюда с исключёнными продуктами.
2. Перебираются сочетания с отсечением заведомо неподходящих веток (если калории уже превышены, дальше не идём).
3. Каждый набор получает оценку: насколько он далёк от цели по калориям, белку, жирам и углеводам, плюс штраф за недостоверные данные и (по желанию) за цену.
4. Лучшие наборы хранятся в куче фиксированного размера; почти одинаковые наборы склеиваются, чтобы выдача была разнообразной.
5. Правила здравого смысла: не больше одного основного блюда и одного напитка, соус — только вместе с едой.

На меню из 250 позиций подбор занимает около 6 мс при бюджете 100 мс.

## 10. Откуда данные

- **Заведения** — 14 604 настоящих места из OpenStreetMap в Москве, области и Петербурге: 116 сетей (вместе с магазинами ВкусВилл, Перекрёсток и Азбука вкуса) и 9 567 отдельных мест; берутся только места, подтверждённые за последние 3 года.
- **Меню с КБЖУ** — только из официальных источников сетей: их сайтов, приложений и опубликованных таблиц. Сейчас это 25 сетей и 3682 блюда. Для каждой сети есть скрипт разбора и отчёт с адресом источника, датой и списком пропущенных строк (`tool/menus/`, таблица — в `menus.md`).
- **Проверки при разборе**: калории сверяются с белками, жирами и углеводами (строки, где цифры не сходятся, отбрасываются); значения на 100 г пересчитываются на вес порции; в каталог берутся только порции на одного (без сетов, тортов целиком, больших пицц); отметки аллергенов строятся по составу и названию с запасом.
- **Типичные меню** — у 13 158 заведений без официального меню: типичное меню их вида (кофейня, пиццерия, столовая, шаурма, магазин с готовой едой и ещё 10 видов) с уровнем C: КБЖУ — оценка по похожим блюдам официальных меню, с диапазоном калорий. Так подбор видит все заведения, а не только 10% (`approximate-menus.md`).
- **Фото меню** от пользователей распознаются Tesseract и проходят модерацию; одобренное меню заменяет типичное.
- **Жалобы** переводят блюдо на перепроверку.

Цвет достоверности на карте: зелёный — официальная таблица сети, жёлтый — меню из фото после модерации, красный — оценка, серый — данных нет.

## 11. Безопасность и приватность

- Профиль, дневник и норма хранятся только на телефоне; есть кнопка «Удалить все данные».
- В запросах нет идентификатора пользователя, токенов и cookies; жалобы привязаны к обезличенному хешу.
- Пароль админки хранится как bcrypt-хеш, без него сервер не запускается; вход ограничен по числу попыток; формы защищены от CSRF.
- Порты базы и хранилища открыты только на локальном адресе; сервер в контейнере работает от непривилегированного пользователя.

## 13. Как запустить

- **Проще всего**: установить `norma-ryadom-offline.apk` (лежит в архиве и в GitHub Releases). Работает без интернета и сервера; местоположение — Москва-Сити, район можно сменить в профиле.
- **С сервером**: создать `.env` по образцу `.env.example` (пароли и bcrypt-хеш пароля админки), затем `(cd server && ./gradlew bootJar)` и `docker compose up -d --build --wait` — поднимутся база, хранилище и сервер. Swagger — `http://localhost:8080/swagger-ui.html`, админка — `http://localhost:8080/admin`.
- **Клиент из исходников**: `cd app && flutter run --flavor demo --dart-define=API_BASE_URL=http://10.0.2.2:8080` для эмулятора Android; для iOS-симулятора — `flutter run --dart-define=API_BASE_URL=http://localhost:8080`. Подробно — в `README.md`.

## 15. Частые вопросы на защите

**Почему цифры можно считать достоверными?** Берутся только официальные данные сетей, у каждой строки есть источник и дата, калории сверяются с БЖУ, а приложение прямо показывает уровень достоверности.

**Почему не взять данные с агрегаторов доставки?** Там нет гарантии, что цифры от сети, и нет права их переиспользовать; приложение честно помечает заведения без данных.

**Зачем свой алгоритм, если можно отсортировать блюда по калориям?** Сортировка подбирает одно блюдо, а нужен набор, который одновременно укладывается в калории, белок, жиры и углеводы и не содержит исключённых продуктов. Это комбинаторная задача.

**Где хранятся мои данные?** Только на телефоне. Сервер не знает, кто делает запрос.

**Что будет, если сеть поменяет меню?** Скрипт разбора запускается заново, импорт обновляет блюда без дублей, версия меню растёт, кэш сбрасывается автоматически.

**Почему Flutter, а не нативная разработка?** Один код для Android, iOS и веба; для курсового проекта это экономит время без потери качества интерфейса.

**Почему Kotlin и Spring Boot?** Строгая типизация, зрелая экосистема для веб-серверов, готовые решения для безопасности, миграций и мониторинга.

**Почему PostGIS?** Поиск «заведения в радиусе 1,5 км» — одна функция с геоиндексом, а не ручной перебор координат.
