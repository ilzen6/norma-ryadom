# «Норма рядом» — о проекте и кто что делал

Общий документ команды для защиты: сначала что за проект и как он работает, затем вклад каждого участника — что сделано, где это в коде, как работает и как ответить на вопросы.

## Часть 1. О проекте

### Что это

«Норма рядом» — мобильное приложение-гид по питанию вне дома. Человек, который следит за питанием, дома считает калории по этикеткам, а в кафе выбирает «на глаз» и ошибается на 150–200 ккал за обед. Приложение решает задачу «что взять здесь и сейчас»:

1. считает дневную норму калорий, белков, жиров и углеводов (КБЖУ) по полу, возрасту, росту, весу, активности и цели;
2. делит её на приёмы пищи (завтрак 25%, обед 35%, ужин 30%, перекус 10%);
3. находит заведения рядом и подбирает в них наборы из 1–3 блюд, которые попадают в цель и не содержат исключённых продуктов (например, «без свинины»);
4. честно показывает, насколько можно доверять цифрам;
5. записывает выбранный набор в дневник; умеет связываться с Apple Здоровьем и Health Connect.

### Что умеет

| Экран | Возможности |
|---|---|
| Онбординг | Параметры тела, исключения продуктов, доступ к геолокации или выбор района |
| «Что взять» | Остаток нормы на сегодня, выбор приёма пищи, «Подобрать рядом» — до 20 вариантов; если рядом мало, поиск сам расширяется до 3 и 6 км |
| Набор | КБЖУ, цена, расстояние, уровень достоверности, замена любого блюда, «Записать в дневник» |
| Карта | Заведения с цветом «есть набор под цель / компромисс / нет»; второй режим «По данным» — цвет по достоверности; список заведений; кластеры точек |
| Заведение | Меню с пометками «подходит / можно, но… / не подходит», источник и дата данных, жалоба «Цифры не совпадают», «Закрыто или переехало?», фото меню |
| Дневник | Приёмы пищи за день, прогресс по КБЖУ, запись вручную, учёт еды из других приложений |
| Профиль | Параметры и норма (правка в процентах), район, тема (системная, светлая, тёмная), связь со «Здоровьем», удаление всех данных |
| Админка (веб) | Импорт меню из CSV, модерация фото меню, разбор жалоб на блюда и на точки |

### Как работает

- **Приложение** (Flutter): считает норму и ведёт дневник. Личные данные хранятся только на телефоне, в SQLite.
- **Сервер** (Kotlin + Spring Boot): хранит заведения и меню в PostgreSQL + PostGIS, ищет точки в радиусе одним геозапросом и подбирает наборы алгоритмом перебора с отсечением. Фото меню кладёт в S3-хранилище SeaweedFS и распознаёт Tesseract.
- **Связь:** в запросе только цель приёма пищи, координаты и исключённые продукты — без имени и идентификатора пользователя.
- **Без сервера:** демо-сборка содержит каталог и тот же алгоритм на Dart. Что результаты совпадают с сервером, проверяет общий эталон `contract/combo-cases.json`.

### Откуда данные и почему им можно доверять

- **Заведения — OpenStreetMap**, 14 285 мест в Москве, области и Петербурге. Берутся только подтверждённые за последние 3 года; закрытые отсеиваются; у каждой точки хранится дата подтверждения.
- **КБЖУ — только официальные данные сетей**: 25 сетей, 3682 блюда. Это сайты, API приложений и таблицы самих сетей. У каждого блюда хранятся источник и дата; калории сверяются с белками, жирами и углеводами.
- **Пользователи помогают поддерживать актуальность.** Жалоба «цифры не совпадают» или «закрыто» от трёх человек отправляет блюдо или точку на проверку модератору. Фото меню попадают в каталог только после модерации.
- **Уровни достоверности:** A — официальная таблица сети (зелёный), B — меню с фото после модерации (жёлтый), C — оценка (красный); нет данных — серый.

### Качество

- **Тесты:**
  - сервер — 171: модульные, интеграционные на настоящей базе в Docker, архитектурные, контрактные;
  - приложение — около 190: модульные и виджет-тесты, покрытие строк больше 96%;
  - 5 сквозных сценариев в браузере.
- **Проверки на каждый push** (GitHub Actions): тесты, анализаторы кода, сборки Android, сквозные сценарии.
- **Правила кода:** без комментариев (пояснения в `docs/`), интерфейс и названия тестов на русском, точные версии зависимостей.

### Егор Соловьёв — уровень данных заведения по большинству блюд

**Задача.** На карте в режиме «По данным» точка окрашивается по уровню достоверности её меню: A — официальная таблица сети, B — меню с фото после модерации, C — оценка. Раньше сервер брал **лучший** уровень среди блюд заведения (`min` по буквам A < B < C). Заведение, где одно блюдо из официальной таблицы, а остальные десять из фото, показывалось зелёным, то есть надёжнее, чем на самом деле. Нужно было брать уровень, который у **большинства** блюд.

**Что сделано.**

1. В файле `server/src/main/kotlin/ru/normaryadom/catalog/persistence/VenueRows.kt` в SQL-запросе заменена агрегатная функция:

   ```
   SELECT mode() WITHIN GROUP (ORDER BY item.source_kind)
   FROM menu_item item
   WHERE (item.venue_id = v.id OR item.chain_id = v.chain_id) AND item.is_available AND NOT item.under_review
   ```

   Было `SELECT min(item.source_kind)`.

2. В файле `server/src/test/kotlin/ru/normaryadom/recommendation/VenueApiIT.kt` добавлен тест «отмечает заведение уровнем данных, который у большинства его блюд».

**Как это работает.**

- `mode() WITHIN GROUP (ORDER BY …)` — агрегатная функция PostgreSQL «мода»: она возвращает самое частое значение в группе. Если значений поровну, берётся первое по порядку сортировки, то есть более надёжный уровень.
- В расчёт берутся только доступные блюда, не отправленные на перепроверку: и общие блюда сети (`chain_id`), и собственные блюда точки (`venue_id`).
- Путь значения: SQL в `VenueRows` → поле `Venue.dataQuality` → ответ API `GET /api/v1/venues` (поле `dataQuality`) → в приложении `app/lib/ui/map/map_screen.dart` выбирает цвет точки в режиме «По данным».

**Тест.**

- Тест наследует `IntegrationTest`: он поднимает настоящий PostgreSQL + PostGIS в Docker через Testcontainers.
- Создаётся сеть «Боулы» с тремя официальными блюдами (уровень A) и точкой у Москва-Сити.
- К точке добавляются четыре своих блюда из меню (уровень B).
- Запрос `GET /api/v1/venues` должен вернуть `dataQuality = "B"`: блюд B больше, чем A. Со старым `min` вернулось бы A, и тест бы упал.

**Как показать.**

1. Открыть `server` в IntelliJ IDEA, затем файл `VenueRows.kt` — константа `SELECT_COLUMNS`, подзапрос `data_quality`.
2. Открыть `VenueApiIT.kt` и запустить тест зелёным треугольником (нужен запущенный Docker) или командой:
   ```bash
   cd server && ./gradlew test --tests '*VenueApiIT'
   ```

**Возможные вопросы.**

- *Почему `mode`, а не среднее?* Уровни — категории (A, B, C), а не числа; для категорий «типичное значение» — это мода.
- *Почему не считать в Kotlin?* Пришлось бы загружать в память все блюда каждой точки; в SQL база считает это одним подзапросом прямо при выборке точек.
- *Что будет при равенстве?* Мода берёт первое значение по сортировке, то есть более надёжный уровень.
- *Почему интеграционный, а не модульный тест?* Проверяется именно SQL. Его правильность можно доказать только на настоящей PostgreSQL, поэтому тест идёт через Testcontainers.

### Руслан Абилов — подсказка «Что значат цвета» на карте

**Задача.** На карте есть переключатель режимов «По норме / По данным». В режиме «По данным» точки окрашены в зелёный, жёлтый, красный и серый, но пользователю было неочевидно, что означает каждый цвет. Нужна была подсказка прямо у переключателя.

**Что сделано.**

1. **`app/lib/ui/map/map_screen.dart`**
   - Переключатель `SegmentedButton` (`Key('map-coloring')`) помещён в строку `Row` рядом с кнопкой `IconButton` со значком «i» (`Key('map-coloring-help')`, всплывающая подпись «Что значат цвета»).
   - По нажатию `showDialog` открывает диалог — новый виджет `_ColoringHelp`. Это `AlertDialog` со списком из четырёх строк «цветной кружок + пояснение» и кнопкой «Закрыть».
   - Цвета берутся из общей палитры приложения (`context.palette`: `good`, `warn`, `bad`, `inkSubtle`). Поэтому подсказка совпадает с цветами точек на карте и правильно выглядит в светлой и тёмной теме.
2. **`app/lib/l10n/app_ru.arb`** — пять новых текстов: заголовок «Что значат цвета» и четыре пояснения (зелёный — официальная таблица сети, жёлтый — меню с фото после модерации, красный — оценка, серый — данных нет). По правилам проекта тексты интерфейса хранятся только здесь, а не в коде.
3. **`app/test/ui/tabs_test.dart`** — виджет-тест «карта объясняет, что значат цвета уровней данных».

**Как это работает.**

- Режим карты хранится в провайдере Riverpod `mapColoringProvider`: переключатель меняет его, карта перерисовывает точки.
- Кнопка подсказки не меняет состояние, она только показывает диалог. Поэтому диалог — простой `StatelessWidget`.
- Тексты берутся через `context.l10n` — сгенерированный из `app_ru.arb` класс локализации.

**Тест.**

- `TestHarness` запускает приложение с фейковыми репозиториями: сервер не нужен, заведения подставляются из теста.
- Тест открывает вкладку «Карта», разворачивает список, прокручивает до кнопки подсказки и нажимает её.
- Проверяет, что открылся диалог «Что значат цвета» с текстом «Красный — оценка, цифры приблизительные.».
- Нажимает «Закрыть» и проверяет, что диалог исчез.

**Как показать.**

1. Открыть `app` в VS Code, затем `lib/ui/map/map_screen.dart` — найти `map-coloring-help` и класс `_ColoringHelp`.
2. Запустить приложение («Демо без сервера»), открыть «Карта», переключить на «По данным» и нажать «i».
3. Запустить тест:
   ```bash
   cd app && flutter test test/ui/tabs_test.dart --plain-name 'карта объясняет'
   ```

**Возможные вопросы.**

- *Почему диалог, а не подпись под переключателем?* Подпись занимала бы место на маленьком экране постоянно, а пояснение нужно один раз.
- *Почему цвета не заданы прямо в диалоге?* Они берутся из общей палитры: если поменять цвет точки на карте, подсказка поменяется вместе с ним, и тёмная тема работает сама.
- *Зачем тексты в `app_ru.arb`?* Все тексты интерфейса в одном файле: их легко проверить, исправить и перевести, а код не смешивается с текстом.
- *Что проверяет тест?* Что кнопка есть, диалог открывается с нужным текстом и закрывается — то есть сценарий пользователя целиком.
