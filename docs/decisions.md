# Архитектура и решения

Документ объясняет, как устроен проект и почему. Отдельно перечислены места, где реализация расходится с исходным документом «Норма рядом: разбор идеи и план реализации», и причина каждого расхождения.

## 1. Общая схема

- **Монолит с модулями**, как в разделе 9.2 документа. Модули — пакеты верхнего уровня `catalog`, `geo`, `optimizer`, `recommendation`, `intake`, `admin`, `web`, `common`. Отсутствие циклов между ними и независимость алгоритма от фреймворка проверяются тестом `ArchitectureTest` (ArchUnit).
- **Профиль, норма и дневник живут только на устройстве** (drift/SQLite). На сервер уходит цель приёма пищи, теги исключения и координаты поиска — без идентификатора пользователя (раздел 6.2). Поэтому на сервере нет пользовательских объектов и, как следствие, нет поверхности для IDOR; закрытая часть — только админка.
- **Подбор на сервере**: меню и алгоритм в одном месте, улучшение алгоритма не требует релиза клиента.

## 2. Сервер

| Решение | Почему | Почему не альтернатива |
|---|---|---|
| Spring Boot **4.1**, Kotlin 2.3, JDK 21 | В документе указан Boot 3, но бесплатная поддержка 3.5 закончилась в июне 2026, у 4.0 — заканчивается 31.12.2026. Новые проекты начинаем на 4.1. | Boot 3.5 — без обновлений безопасности к моменту защиты. |
| SQL на `JdbcClient` вместо Spring Data JDBC | Геозапросы PostGIS, массивы тегов и `ON CONFLICT` проще и прозрачнее писать явным SQL; каждый запрос виден и проверяется планом. | Spring Data JDBC потребовал бы конвертеров для `geography` и `text[]` и всё равно ручных запросов для геопоиска. |
| Алгоритм подбора — чистый Kotlin без Spring (`optimizer`) | Легко тестировать: юнит-тесты, проверка свойств jqwik, замер производительности. | — |
| Перебор с отсечением, куча `limit × 4`, диверсификация «не больше одного общего блюда» | Точно по разделу 11 документа. Доказано тестом: на 200 случайных меню результат совпадает с полным перебором без отсечений. | Целочисленный решатель избыточен для 1–3 блюд из 250 позиций; на 250 позициях подбор занимает ~7 мс. |
| Кэш лучших наборов (Caffeine) с ключом «меню + версия меню + округлённая цель» | Раздел 11.3: для карты и «подобрать рядом» подбор по сети выполняется один раз. Версия меню в ключе исключает устаревший ответ после импорта или жалоб (проверено тестом). | Сброс всего кэша при каждом изменении проще, но хуже по нагрузке и легко забыть. |
| Округлённая цель возвращается клиенту (`appliedTarget`) | Пользователь видит, по какой цели реально шёл поиск; замена блюда в найденном наборе идёт по той же цели. | — |
| Хранилище фото — любое S3-совместимое (AWS SDK v2), в Docker — **SeaweedFS** | MinIO больше не публикует образы в Docker Hub, а лицензия AGPL неудобна. Код от конкретного хранилища не зависит: можно подставить MinIO, Ceph или облачный S3. | Хранить фото в БД — раздувает базу и бэкапы. |
| OCR — Tesseract через **tess4j 5.4.0** | Версия tess4j подобрана под системные Leptonica 1.82 / Tesseract 5.3 из Ubuntu 24.04; новые tess4j требуют Leptonica 1.85 и падают при загрузке (найдено тестом). | Облачный OCR — платно и передаёт фото третьей стороне. |
| Распознавание в фоне по расписанию, статус `OCR_FAILED` | Загрузка фото не ждёт OCR; если распознать не вышло, модератор всё равно видит фото и вносит строки вручную. Статуса нет в схеме документа — без него заявка «зависла» бы в `NEW`. | Синхронный OCR в запросе загрузки — долгие ответы и таймауты. |
| Колонка `under_review` у блюда | Раздел 5.6: «три жалобы — блюдо уходит на перепроверку». Блюдо на перепроверке не участвует в подборе, пока модератор не подтвердит, не исправит или не снимет его. | — |
| Ошибки API — Problem Details (RFC 9457) с кодом в `type` и списком `errors` | Клиент различает ошибки по типу, тексты локализует сам; внутренности (SQL, классы) не раскрываются (проверено тестом). | — |
| Ограничение частоты загрузок фото, жалоб и входа в админку — в памяти процесса | Один экземпляр сервера (раздел 9.2). При нескольких экземплярах лимит нужно вынести в Redis. Адреса IPv6 считаются по сети /64, иначе один клиент получил бы бесконечно много адресов. | — |
| Жалоба хранит не адрес, а HMAC-отпечаток с секретным ключом `REPORTER_KEY` | Одна открытая жалоба на блюдо от одного человека (уникальный индекс), адрес по отпечатку не восстановить. | Хранить IP — лишние персональные данные; не хранить ничего — один человек снимает блюдо тремя жалобами. |
| `X-Forwarded-For` учитывается только от прокси из `TRUSTED_PROXIES_REGEX` | По умолчанию заголовок не доверяется, иначе любой клиент обходил бы лимиты подменой. | — |
| Фото перекодируется перед сохранением | Убирает EXIF с геометкой; размер в пикселях проверяется по заголовку до распаковки (защита от «бомбы»). | Хранить оригинал — утечка геолокации пользователя. |
| Цель для кэша округляется «внутрь» | Калории — шаг 10, допуск, жиры и углеводы — вниз до 5 г, белок — вверх до 5 г: найденный набор всегда укладывается в исходную цель пользователя (проверено свойством). | Округление до ближайшего могло бы расширить окно. |
| Админка — серверные страницы Thymeleaf с формой входа и CSRF | Внутренний инструмент (раздел 7.2, экран 7): минимум кода, сессия и CSRF из коробки, доступность проверена axe. | Отдельное SPA добавило бы ещё одно приложение и токены. |

## 3. Клиент

| Решение | Почему | Почему не альтернатива |
|---|---|---|
| Слои по официальному гайду Flutter: View + ViewModel (Riverpod `Notifier`), репозитории и сервисы | Однонаправленный поток данных, бизнес-логика вне виджетов, репозитории подменяются фейками в тестах. | — |
| Карта на **flutter_map** с настраиваемым источником тайлов | Это запасной вариант из раздела 6.1 документа. MapKit требует ключ и не работает в веб-сборке, на которой построены сквозные проверки. Ценность продукта (подбор) от карты не зависит. | Переход на `yandex_maps_mapkit_lite` — отдельная задача, когда будет ключ: интерфейс экрана карты при этом не меняется. |
| Модели API на freezed + json_serializable | Указано в стеке документа. Расхождение с сервером ловят: снимок OpenAPI-контракта в тесте сервера и тесты разбора JSON в клиенте; перечисления переживают неизвестные значения. | Генерация клиента из OpenAPI добавила бы built_value-модели и ещё один генератор. |
| Норма считается на клиенте; на сервере та же формула только в тестах | Раздел 8 документа. Обе реализации проверяются по одному файлу `contract/norm-cases.json`. | — |
| Норма для похудения — 85% расхода, нижние границы 1200/1500 ккал | Раздел 6.3: дефицит не более 20%, безопасный минимум; ручная норма ниже минимума не принимается. | — |
| Шрифты Onest (текст) и Unbounded (заголовки, цифры) под OFL, CanvasKit — вложены в сборку | Приложение не ходит в CDN Google: работает в закрытых сетях и не раскрывает факт использования третьим лицам. Onest — гротеск с хорошей кириллицей, Unbounded даёт крупным числам КБЖУ характер; цифры везде табличные, чтобы не прыгали. | Roboto выглядит как «приложение по умолчанию» и хуже держит крупные цифры. |
| Дизайн-система на токенах `Palette` (светлая и тёмная тема по системе) | Цвета КБЖУ, статусов и карты заданы один раз и проверяются тестами; мягкие статусы вместо красного «нельзя» — приложение про еду не должно ругать. Плавающая стеклянная панель вкладок, карточки без рамок на тонированном фоне, анимация колец и чисел. | Цвета в виджетах расходятся между экранами и ломают тёмную тему. |
| Демо-каталог: 10 вымышленных сетей, 349 точек по адресам реальных заведений общепита из OpenStreetMap | Точки стоят на настоящих кафе и ресторанах (не в реке и не на путях), минимум 60 м друг от друга; генератор `tool/demo/build_demo_venues.py` берёт `places.json` из той же выгрузки, что и подложка. Карта показывает точки в радиусе 3 км (`MAP_RADIUS_METERS`), подбор — в 1,5 км; близкие точки собираются в кластеры с числом. | 25 точек давали пустую карту; случайные координаты попадали бы в реку и дворы. |
| Фон экранов — `Backdrop`: мягкие засветы цветов КБЖУ и топографические линии | Однотонный фон выглядел плоско; линии-«горизонтали» отсылают к теме «рядом» и карте, не мешая чтению: прозрачность не выше 16%, только у верхнего края. | Фото и градиенты на всю площадь спорят с карточками и съедают контраст. |
| Встроенная векторная подложка карты для центра Москвы из OpenStreetMap (ODbL) | Без интернета и без поставщика тайлов карта всё равно показывает воду, парки, дома, дороги, железную дорогу и метро. Данные собирает `tool/basemap/build_basemap.py` на GitHub Actions из выгрузки Geofabrik через osmium и кладёт в ветку `basemap-data`; в сборке — `app/assets/map/basemap.json` (~2,4 МБ, дельта-кодирование координат). Атрибуция показана под списком заведений. | Публичные тайлы OSM запрещают нагрузку от приложений; коммерческие требуют ключ и не работают в закрытой сети. |
| Android: `allowBackup=false` и запрет облачного бэкапа | Профиль и дневник — данные о здоровье, они не должны уходить в облако без отдельного согласия (раздел 6.2). | — |

## 4. Данные

- Схема — раздел 10 документа плюс: `menu_version` у сети и точки (ключ кэша), `under_review` у блюда, `resolved_at` у жалобы, `content_type` и `moderated_at` у заявки с фото, уникальные индексы для идемпотентного импорта, `CHECK` для категорий, неотрицательных значений и диапазона калорий уровня C.
- Первичные ключи — `GENERATED ALWAYS AS IDENTITY`, цены — целые копейки, время — `timestamptz`.
- Геозапрос использует GiST-индекс `venue_location_gix` (план — `docs/reports/explain-nearby-venues.txt`, проверка — `NearbyVenueRepositoryIT`).
- Меню точки сети = меню сети + собственные блюда точки (уровень B после модерации фото).

## 5. Безопасность

- Админка: форма входа, пароль только в виде bcrypt-хеша из переменной окружения; без хеша сервер не стартует (проверено тестом). Все изменения — с CSRF-токеном.
- Actuator наружу отдаёт только `health` и `info`; остальное закрыто. В профиле `prod` выключены Swagger и `api-docs`, логи — в формате ECS JSON.
- Загрузка фото: размер до 8 МБ и до 24 млн пикселей, тип определяется по сигнатуре файла, а не по заявленному `Content-Type`; фото перекодируется без метаданных и отдаётся модератору с `X-Content-Type-Options: nosniff`.
- Вход в админку: не больше 10 попыток с адреса за 15 минут.
- Порты базы, хранилища и сервера в `docker-compose.yml` открыты только на `127.0.0.1`.
- На устройстве: `PRAGMA secure_delete` и `VACUUM` после удаления всех данных, чтобы удалённое не оставалось в файле базы.
- В логах только идентификаторы (заявка, заведение, блюдо); IP-адреса и тексты жалоб не логируются.

## 6. Известные ограничения

- Демо-каталог вымышленный: реальные таблицы сетей собираются по разделу 5.4 документа.
- Уровень C (оценка через LLM) не реализован — в документе он «дальнейшее развитие».
- Ограничение частоты в памяти процесса — достаточно для одного экземпляра.
- Состав приёма пищи строже документа: кроме «не больше одного основного и одного напитка» допускается не больше одного соуса, и соус — только вместе с основным блюдом, гарниром или салатом. Иначе алгоритм добирал калории соусами.
- Образ сервера собирается из готового JAR (`./gradlew bootJar` перед `docker compose build`): так CI и E2E используют один и тот же проверенный артефакт, а образ не тянет Gradle и зависимости.
- Геопоиск читает строки заведений через общий `VenueRows`, а не через репозиторий каталога: запрос с расстоянием и покрытием меню — отдельный, но формат строки один.
